# 07 · 延伸练习 / Extensions

## 1. 支持 C99 的 `//` 注释 / Support line comments

C99 引入 `//`，语义是“到行尾为止”。改动不大但会暴露一个设计问题：`//` 注释**不保留行号**（换行本身不属于注释），所以 `ST_LINE_COMMENT` 遇到 `\n` 要输出换行并回 `ST_NORMAL`，而不是像块注释那样“补换行”。

需要新状态：

```c
ST_SLASH2   /* 刚读到第二个 '/'，确认是行注释 */
```

并且要考虑：`a ///* b` 里 `//` 先成立，后面的 `/*` 不生效。

## 2. 处理续行 / Handle backslash-newline continuation

题面允许假定不存在 `\` + 换行。去掉这个假设后，物理行与逻辑行分离：

- `\` + `\n` 在**任何**状态下都表示“续行”，应当被删除且不计入行号
- 但删除后逻辑行变了，`//` 注释的范围也跟着变

这是真实 C 预处理器的第一步。实现上建议在读取层加一个“逻辑字符”函数，把续行折叠掉，状态机只面对逻辑字符。

## 3. 输出行号映射 / Emit a line map

真实预处理器会输出 `#line` 指令，让编译器把错误定位回原文件。可以做一个变体：除了去注释，还在每行前插入 `#line N "file.c"`。

这会立刻暴露一个事实：**注释内部的行号也必须被跟踪**，否则映射表会在多行注释处断裂。

## 4. 加一个 `-c` 选项统计注释 / Count comments

统计块注释数量、总字符数、最长注释长度。看似简单，但需要判断“注释里的字符串”和“字符串里的注释”，正好是本题状态机的反向应用。

## 5. 用词法分析器生成器重写 / Rewrite with a lexer generator

用 `flex` 描述同样的规则：

```
"/*"([^*]|\*+[^*/])*\*+"/"   { printf(" "); }
\"([^"\\]|\\.)*\"             { ECHO; }
\'([^'\\]|\\.)*\'             { ECHO; }
.|\n                          { ECHO; }
```

然后对比生成代码与手写 DFA 的行为差异。重点观察：flex 的最长匹配规则如何处理 `/* a **/`（贪婪匹配到 `**/` 还是 `*/`），以及未终止注释时 flex 的行为与本题要求是否一致。

## 6. 写一个真正的差分测试 / Differential testing against gcc

```bash
gcc -fpreprocessed -dD -E -P input.c
```

`-fpreprocessed` 让 gcc 跳过宏展开，`-dD` 保留宏定义，`-P` 去掉行标记。用它作为第三方 oracle 与本题实现对比，注意两者的已知差异：

- gcc 会规范化空白
- gcc 对未终止注释报错但退出码可能不同
- gcc 处理 `//` 与本题（C90）不同

差分测试的价值不在于“完全一致”，而在于**每一条不一致都能被解释**。

## 7. 移植到其他语言 / Port the DFA

同样的状态机可以用 Rust 的 `match` + `Iterator` 写成无 `unsafe` 的版本，或用 Go 的 `bufio.Reader` 实现。对比三者的错误处理风格：

- C：返回值 + `errno` 风格的退出码
- Rust：`Result` 把“未终止注释”变成类型系统里的分支
- Go：多返回值 + `error`

同一个自动机，三种语言对“可能失败”这件事的表达能力差别很大——这也是 COS 217 之后学 Rust 时最直观的对照点。
