## 输出解读 / Reading the output

- `TestElection` 中 RPC 总数=4：3 节点选举中，候选者向 2 个 peer 各发 1 次投票请求，加上落选节点随后发起的另一次选举的 2 次请求——真实反映了随机超时打破僵局的过程。
  *RPC count = 4 reflects a split vote followed by a retry — randomized timeouts in action.*
- `TestPartitionSafety` 中 `commitIndex=0` 是最关键的一行：它证明少数派 leader **不能提交**。
  *`commitIndex=0` is the most important line: it proves the minority leader cannot commit.*
- 网络恢复后日志收敛为 `[{2 majority-write}]`：少数派未提交的 `minority-write` 被多数派的日志覆盖，符合安全性。
  *After healing, the log converged to the majority's entry — the uncommitted minority write was correctly overwritten.*

## 失败案例与排查 / Failures and debugging

| 症状 / Symptom | 原因 / Cause | 修复 / Fix |
|---|---|---|
| 选举迟迟不结束 / Election stalls | 多个节点同时超时，反复平分选票 / simultaneous timeouts cause repeated split votes | 随机化选举超时（180–320 ms）/ randomized election timeout |
| 少数派 leader 提交了日志 / Minority leader commits | 提交规则只看复制数量，没检查 term / commit rule ignored term | 加上 `log[n].Term == currentTerm` / added the term check |
| 日志冲突后 follower 仍有旧条目 / Stale entries after conflict | 截断时没有删除冲突 index 之后的条目 / truncation didn't remove suffix | `rf.log = rf.log[:idx]` 后再追加 / truncate before append |
| `go test -race` 报 data race | 在持锁外读取 `log` / `nextIndex` / reading shared state without lock | 所有共享字段访问都包在 `rf.mu` 内 / guard all shared state with `rf.mu` |
| `nextIndex` 回退到 0 / nextIndex underflows | 首次复制时 `prevLogIndex = -1` / first append used -1 | 用 index 0 作哨兵，回退下限为 1 / sentinel at index 0, floor at 1 |

> **English:** All four tests passed: election (one leader, term 1, 4 RPCs), log replication (the same three commands applied on all three nodes), failover (a new leader replicated a post-crash command), and partition safety (the minority leader accepted a write but kept commitIndex at 0). The race detector reported no data races in 2.984s.
