# 02 · 设计思路 / Design rationale

## 整体架构 / Architecture

```text
                    ┌──────────────────────────────┐
   Client ──Start──▶│  Leader (node 1, term 2)     │
                    │  log: [dummy][SET a=1]...    │
                    └───────┬──────────┬───────────┘
                            │          │
             AppendEntries  │          │  AppendEntries
                            ▼          ▼
                   ┌────────────┐  ┌────────────┐
                   │ Follower 0 │  │ Follower 2 │
                   └─────┬──────┘  └─────┬──────┘
                         │               │
                   applyCh◀───────────────┘
                   (每条已提交命令 / each committed command)
```

三个核心循环 / Three core loops:

1. **事件循环 `run()`**：leader 定期广播心跳；follower/candidate 在选举超时后发起选举。
   *`run()`: leaders broadcast heartbeats; followers/candidates start elections on timeout.*
2. **应用循环 `applyLoop()`**：把 `commitIndex` 之前的条目投递给上层。
   *`applyLoop()`: delivers entries up to `commitIndex` to the application.*
3. **RPC 处理 `handleRequestVote` / `handleAppendEntries`**：收到消息时更新状态。

> **English:** Separating the "consensus loops" from the "apply loop" is important: applying to the state machine must never block the protocol, or a slow application would stall heartbeats and trigger spurious elections.

## 关键决策 / Key decisions

| 决策 / Decision | 选择 / Choice | 理由 / Why |
|---|---|---|
| 领导模型 / Leadership | 强 leader，只有 leader 接命令 / strong leader | 把共识拆成「选 leader + 复制」，大幅简化推理 / decomposes consensus into election + replication |
| 选举超时 / Election timeout | 随机 180–320 ms / randomized | 避免平分选票；3 节点测试中约 250 ms 选出 leader / avoids split votes; ~250 ms in our 3-node test |
| 心跳间隔 / Heartbeat | 60 ms（远小于最小超时 180 ms）/ 60 ms (well below 180 ms min) | 抑制 follower 发起无谓选举 / suppresses spurious elections |
| 日志索引 / Log index | index 0 为哨兵，term=0 / sentinel at index 0 | 让 `prevLogIndex=0` 的首次复制有统一表示 / uniform representation for the first append |
| 持久化 / Persistence | 每次状态变更写回 persister | term 和投票必须在重启后保留，否则违反安全性 / term and vote must survive restarts for safety |
| 提交规则 / Commit rule | 多数派复制 **且** `log[n].Term == currentTerm` | 这是 Raft 安全性的关键：不能直接提交旧 term 的条目（Figure 8 场景）/ critical for safety; see Figure 8 |
| 日志回退 / Backtracking | `nextIndex--` 逐条回退 | 简单正确；教学版足够，生产版可用冲突提示优化 / simple and correct; production can optimize with conflict hints |

## 备选方案 / Alternatives

- **Paxos**：更通用但难以教学与实现；Raft 的可理解性是本项目选它的原因。
  *Paxos is more general but harder to teach and implement; Raft's understandability is why we chose it.*
- **用真实网络库（gRPC）**：会增加环境依赖；内存网络能精确注入宕机和分区，更适合学习。
  *A real RPC library adds dependencies; an in-memory network lets us inject crashes and partitions precisely.*
- **立即回退到冲突 term**：更快但更复杂；教学版先掌握逐条回退，再在 07 练习里优化。
  *Jumping straight to the conflicting term is faster but more complex; chapter 07 asks readers to implement it.*

> **English:** The single most important design decision is the commit rule requiring `log[n].Term == currentTerm`. Without it, a leader could commit an entry from an old term that a majority actually lacks — the classic Raft Figure 8 trap.

## 状态变量速查 / State variable reference

| 变量 / Variable | 含义 / Meaning |
|---|---|
| `currentTerm` | 当前任期 / current term |
| `votedFor` | 本任期内投给谁，-1 表示未投 / whom we voted for this term |
| `log[]` | 日志条目序列 / sequence of log entries |
| `commitIndex` | 已知已提交的最大 index / highest committed index |
| `lastApplied` | 已应用到状态机的最大 index / highest applied index |
| `nextIndex[]` | leader 认为发给每个 peer 的下一条 index / next index to send per peer |
| `matchIndex[]` | leader 认为每个 peer 已复制的最大 index / highest replicated index per peer |
