# 06 · 踩坑清单 / Pitfalls

## 1. 提交旧 term 的条目（Figure 8 陷阱）/ Committing old-term entries

- 症状 / Symptom：新 leader 似乎提交成功，但该条目在后续 leader 中消失。
  *An entry appears committed but vanishes under a later leader.*
- 原因 / Cause：提交规则只看「多数派复制」，没检查条目是否属于当前 term。
  *Commit rule checked only replication count, not the entry's term.*
- 修复 / Fix：`rf.log[n].Term == rf.currentTerm` 才允许提交。
- 实测 / Evidence：`TestPartitionSafety` 中少数派 `commitIndex` 始终为 0。

> **English:** This is the single most common correctness bug in student Raft implementations. The entry from an old term may be replicated on a majority yet still be unsafe to commit.

## 2. 平分选票 / Split votes

- 症状 / Symptom：集群长时间没有 leader，term 一直增长。
- 原因 / Cause：两节点同时超时、同时投票给自己。
- 修复 / Fix：选举超时随机化；心跳间隔 60 ms 远小于最小超时 180 ms。

## 3. 日志截断漏掉后缀 / Truncation misses the suffix

- 症状 / Symptom：冲突条目被替换，但它后面的旧条目仍在。
- 原因 / Cause：只覆盖冲突位置，没有删除其后的所有条目。
- 修复 / Fix：先 `rf.log = rf.log[:idx]`，再追加新条目。

## 4. 数据竞争 / Data races

- 症状 / Symptom：`go test -race` 报警；偶发的诡异状态。
- 原因 / Cause：`sendAppendEntries` 中读取 `nextIndex` 后释放锁，回复回来时状态已变。
- 修复 / Fix：RPC 构造阶段持锁读快照；回复处理阶段重新持锁并校验 `state` 与 `term` 未变。

## 5. 心跳与选举超时太接近 / Heartbeat too close to election timeout

- 症状 / Symptom：leader 正常却频繁被挑战。
- 原因 / Cause：网络延迟导致 follower 误以为 leader 挂了。
- 修复 / Fix：心跳 60 ms，最小选举超时 180 ms，留 3 倍余量；本实现网络延迟 2 ms。

## 6. `nextIndex` 下溢 / nextIndex underflow

- 症状 / Symptom：panic 或 `prevLogIndex = -1` 的一致性检查失败。
- 修复 / Fix：index 0 放哨兵条目；回退下限为 1。
