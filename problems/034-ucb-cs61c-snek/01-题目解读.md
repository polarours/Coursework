# 01 · 题目解读 / Reading the problem

## 一个字符同时是方向和身份 / One character carries both identity and heading

棋盘上每个蛇格是一个字符：

```
# d>D    *         #
```

`d` 是尾巴，`>` 是身体，`D` 是头。三者都隐含了“这条蛇朝右走”。这个设计把三样信息压进一个字节：

- 这个格子属于哪条蛇的哪个部位（头 / 身 / 尾）
- 这条蛇的朝向
- 下一步该往哪个格子移动

代价是字符集必须严格分区：小写 `wasd` 只能出现在尾巴上，`^<v>` 只能出现在身体上，大写 `WASD` 只能出现在头上。`is_tail`/`is_head`/`is_snake` 三个判定函数就是在维护这个分区。

> **English:** The board is the state. A single character encodes body part, heading, and next position at once — which is why the whole game needs no separate velocity array.

## 为什么尾字符是方向 / Why the tail carries a direction

移动时尾巴要“往上跟一格”。怎么知道往哪跟？答案是：沿着身体的方向。尾字符 `d` 表示这条蛇的尾巴朝右延伸，所以尾巴的下一格在右边。

这让 `update_tail` 变成三步：

1. 清空当前尾格
2. 把尾的下一格（当前是 `>`）改成尾字符 `d`
3. 结构体里的 `tail_row`/`tail_col` 指向新位置

不需要遍历整条蛇，O(1) 完成。

## 死亡是一步之内的判定 / Death is decided before moving

规则说“头撞墙或撞蛇就死”。实现上必须在**移动之前**检查目标格：

```c
char next = next_square(game, i);
if (next == '#' || is_snake(next)) { /* 死亡 */ }
```

如果先移动再检查，头已经覆盖了目标格，原来的信息就丢了。`next_square` 被单独列成一个任务（4.2）并强调“不修改任何状态”，正是为了让这个“先看后动”的顺序变得自然。

## 七次提交的形状 / Why the tasks are split this way

题目把实现切成 7 个任务，每个都能独立测试：

| Task | 可独立验证的原因 |
|---|---|
| 1 默认棋盘 | 纯数据，打印出来就能比对 |
| 2 释放 | Valgrind 能直接判定 |
| 3 打印 | 输出比对 |
| 4.1 helper | 纯函数，输入输出确定 |
| 4.2–4.4 | 单步操作，棋盘前后可比对 |
| 4.5 | 组合，但输入输出仍是棋盘 |
| 5 加载 | 文件 → 结构体，可比对 |
| 6 初始化 | 棋盘 → 蛇数组，可比对 |
| 7 main | 端到端 |

这种切法的价值在于：出错时能立刻定位到某一层，而不是对着一个整体 diff 猜。

## 被规格隐藏的难点 / What the spec understates

三处容易低估：

1. **`create_default_game` 要自带蛇。** 规格的 Task 1 只描述棋盘，但官方单测要求 `num_snakes == 1`。如果按字面理解只建棋盘，单测立刻失败。
2. **`load_board` 的行不等长。** 测试文件 `13-sus-in.snk` 里有 20 列和 24 列混排的棋盘，用固定宽度二维数组会越界。
3. **`unit_tests.c` 直接 include `game.c`。** 它要测 `static` 函数，所以把实现文件整个包含进来；编译时再加 `game.c` 会导致符号重复定义。
