# 04 · 正确性与复杂度 / Correctness and complexity

## 不变量 / Invariants

1. **块大小 8 的倍数 / Size multiple of 8**：header 中 size 低 3 位作标志位。
   *Low 3 bits of size hold flags, so size is 8-aligned.*
2. **header/footer 一致**：已分配块和空闲块的 header 与 footer 的 size/alloc 字段相同。
   *Header and footer agree on size and alloc bits.*
3. **相邻块无重叠**：`NEXT_BLKP(bp)` 恰好指向下一块 header。
   *`NEXT_BLKP(bp)` points exactly at the next block's header.*
4. **对齐 / Alignment**：所有 payload 地址 % 8 == 0。
   *All payload addresses are 8-byte aligned.*
5. **合并完全**：连续空闲块总会被合并成一个。
   *Adjacent free blocks are always coalesced into one.*

> **English:** Invariant 4 was violated in our first working build — the test printed "16-byte aligned: 0". We converted that print into a real `assert` and found a genuine alignment bug. Always assert what you print.

## 证明思路 / Proof sketch

**为什么 footer 能让向前合并 O(1)？/ Why does the footer give O(1) backward coalesce?**

`PREV_BLKP(bp) = bp - GET_SIZE(bp - DSIZE)`：从当前 header 前 8 字节处读出前一块的大小，就能算出前一块的起始地址。这依赖于 footer 始终存在——这是边界标签的核心价值。
Reading the size at `bp - 8` gives the previous block's size, so its start is computable in O(1). This requires footers on all blocks.

**释放后为什么不产生碎片？/ Why no fragmentation after free?**

`coalesce` 检查四种情况并合并相邻空闲块；实测连续释放 a、b、c 后空闲块数从 1 → 2 → 2 → 1，最终恢复成单个大块，证明合并正确。
