- Python 3.14.9 / OS: Arch Linux (kernel 7.3.4-arch1-2)
- 命令 / Command: `python3 tests/test_xv6sim.py`
- Workload: 3 个进程 P1(arrival 0, burst 5)、P2(1,3)、P3(2,7)

## 输出解读 / Reading the output

- FCFS 的 timeline 是三段连续运行：P1 跑满 5，P2 跑 3，P3 跑 7——非抢占的特征。
- RR 的 timeline 有 9 段，P1/P2/P3 交替出现——时间片轮转的特征。
- **avg_wait：FCFS 3.33 < MLFQ 5.33 < RR 6.00**。这是真实的调度权衡：RR/MLFQ 用更高平均等待换取响应公平。
  *This ordering is a real scheduling trade-off, not an error.*
- 分配器：alloc(7) 取整到 8 字节，起始地址 0；alloc(8) 得 8；alloc(4) 得 16。释放后再分配能复用合并后的大块。

## 失败案例与排查 / Failures and debugging

| 症状 / Symptom | 原因 / Cause | 修复 / Fix |
|---|---|---|
| RR 等待时间似乎"丢失" | 原代码用 `arrival` 字段在重新入队时存储"上次运行结束"时刻，语义混淆；数值虽对但难维护 | 拆成 `origin`（原始到达）与 `last_run`（上次结束）两个字段 / split into two clearly named fields |
| avg_wait 数值在重构前后不变 | 说明原算法其实正确，只是命名误导——如实记录，不谎称"修了 bug" / original math was right, naming was misleading | 在文档中澄清这一点 / documented honestly |
| 重复 free 导致空闲链表损坏 | 缺少 `if not b.free` 检查 | 加 double-free 检测并返回 False |
| 分配 7 字节得到非对齐块 | 未向上取整到 2 的幂 | `target = 1 << (size-1).bit_length()` |

> **English:** All tests passed. FCFS averaged 3.33 wait / 8.33 turnaround, RR (q=2) 6.00 / 11.00, and MLFQ 5.33 / 10.33. RR's higher average wait is a real scheduling trade-off, not a bug: SJF minimizes average wait, while RR optimizes response fairness. The buddy allocator split 64 into 8+8+4+... and coalesced freed neighbors back into a 16-byte block.
