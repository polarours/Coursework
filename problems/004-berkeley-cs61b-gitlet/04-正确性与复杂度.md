# 04 · 正确性与复杂度 / Correctness and complexity

## 不变量 / Invariants

1. **内容寻址 / Content addressing**：对象的文件名 = 其内容 SHA-1；内容不变则 uid 不变。
   *Object filename equals SHA-1 of its content; unchanged content means unchanged uid.*
2. **提交不可变 / Commit immutability**：提交一旦创建不再修改；新提交通过 parent 链接。
   *Commits are immutable; new ones link via parent.*
3. **HEAD 一致 / HEAD consistency**：HEAD 与当前分支指向同一提交。
   *HEAD and the current branch point to the same commit.*
4. **暂存区清空 / Staging cleared**：commit 成功后暂存区为空。
   *Staging area is empty after a successful commit.*

> **English:** Invariant 1 is enforced by an `assert uid == c.uid` in `_save_commit`. When this failed during development, it caught a subtle double-hashing bug before it corrupted the repo.

## 证明思路 / Proof sketch

**为什么 checkout 能恢复正确内容？/ Why does checkout restore the right content?**

提交树中存的是 blob 的哈希，blob 内容由哈希寻址且不可变。因此只要 HEAD 指向的提交正确，取出的 blob 内容一定与该提交时的文件内容一致。
The commit tree stores blob hashes; blobs are immutable and addressed by hash. As long as HEAD is correct, the retrieved blob is exactly the file content at commit time.

实测：写入 `broken content` 后 checkout，文件内容恢复为 `hello gitlet\n`——验证成功。

**log 的顺序 / Log order**

沿 parent 链从 HEAD 回溯，天然得到 newest-first 顺序；实测输出为 second → first → initial。

## 复杂度 / Complexity

| 操作 / Operation | 时间 / Time | 空间 / Space |
|---|---|---|
| init | O(1) | O(1) |
| add | O(文件大小) / O(file size) | O(文件大小) |
| commit | O(文件数 + 历史长度) / O(files + history) | O(文件数) |
| log | O(历史长度) / O(history length) | O(history) |
| checkout | O(文件大小) | O(file size) |
